### 1.1 Node types (preserved exactly — §6.3)

| Node type | Minimum implied properties | Notes |

| `Constraint` | `description`, `category` | |
| `Standard` | `description`, `category` | |
| `Preference` | `description`, `scope` | `scope` distinguishes project vs global |
| `Event` | `description`, `occurredAt`, `type` | `type` ∈ added / rejected / migrated / changed |

Every stored memory also carries the shared metadata contract (§7.5): `id`, `extractedAt`, `confidence`, `sourceRef`, `importance`, `author` (see `SHARED_MEMORY_METADATA`).

### 1.2 Relationship types (preserved exactly — §6.4)

`USES`, `HOSTED_ON`, `DEPENDS_ON`, `PART_OF`, `DECIDED_ON`, `SUPERSEDES`, `REJECTED`, `AFFECTS`

Suggested semantics in the spec are non-binding; no additional relationship types may be added without recording an open decision (§32).

### 1.3 Constraints (baseline decision, P1-T02 — §6.5)

Spec §6.5 requires constraints but does not enumerate them; the baseline (in `ontology.ts#graphConstraintStatements`):

- unique `id` per node type (`CREATE CONSTRAINT <type>_id_unique ... REQUIRE n.id IS UNIQUE`);
- unique `projectId` on `Project`;
- project-scoping index on `projectId` for all other node types (§6.6 scoping).

### 1.4 Mutation rules (§6.9)

No in-place mutation of memories: state changes are expressed through versioning (§13) and `SUPERSEDES` / `REJECTED` relationships, with an audit record (`memory_versions`).

## 3. Relational schema (spec §9.1 — PostgreSQL)

| Table | Purpose | Spec |
|---|---|---|
| `projects` | Part 1's project reference row (id matches Part 2's project id; identity produced by Part 2, §3.2). Parent of the project-scoped tables | §9.1, §3.2 |
| `memories` | facts/patterns/rules/standards/constraints/preferences with §7.5 metadata, status (`active`/`archived`/`superseded`), access stats | §7, §13, §16 |
| `decisions` | decision memory (decision, reason, alternatives, §10.2 status, decided_at, supersession link) | §10, §13 |
| `events` | dated events (`added`/`rejected`/`migrated`/`changed`) | §11, §6.3 |
| `conflict_reports` | pending/resolved conflict reports with resolution outcome | §12 |
| `memory_versions` | append-only state-transition audit | §13 |
| `ppb_telemetry` | per-stage telemetry (no secrets/PII) | §27, IF-10 |
| `ppb_meta` | seeded metadata: ontology version + placeholder embedding config (OD-2) | §9.1 seed |
| `schema_migrations` | applied migration versions (runner-managed) | §9.5, IF-11 |

**Foreign keys (§9.1):** `memories`, `decisions`, `events` and `conflict_reports` reference `projects(id)`; `memories.superseded_by` and `decisions.superseded_by` are self-references. Two columns are deliberately polymorphic and therefore carry no FK: `conflict_reports.existing_memory_id` (fact/decision/event) and `memory_versions.memory_id` (memories or decisions) — both recorded as implementation decisions.

**Decision status axes (§10.2 vs §13):** `decisions.status` uses §10.2's vocabulary (`accepted`/`rejected`/`superseded`, "preserve exactly"); the §13 memory lifecycle (`active`/`archived`/`superseded`) is recorded in `memory_versions` for the decision's underlying memory (§13.7).

Severity scale on `conflict_reports.severity` is intentionally unconstrained — **PLACEHOLDER pending §32**.

## 7. Migrations (P1-T02)

- Registry: `PPB_MIGRATIONS` in `storage/migrations/index.ts`; runner: `storage/migrate.ts` (`runMigrations` applies, `rollbackMigrations` reverts). Every migration carries both `sql` (up) and `down` (rollback) and runs in its own transaction; applied versions are recorded in `schema_migrations`. Both functions take an injected query interface so they are unit-testable without a database.
- `001_init` — core relational schema: `projects` + FK-linked `memories`/`decisions`/`events`/`conflict_reports`, `memory_versions`, `ppb_telemetry` (applies without pgvector).
- `002_embeddings` — pgvector extension + `embeddings` table (requires pgvector).
- `003_seed_meta` — seed data: `ppb_meta` rows (`ontology_version`, `embedding_model`, `embedding_dim`) inserted idempotently (`ON CONFLICT DO NOTHING`) — §9.1's "seed data".
- `004_write_path` / `005_embedding_index` — outbox + HNSW index (see §11/§12).
- `006_relationships` — **Tier 2** `graph_relationships` table (`id`, `project_id`, `from_id`, `relationship_type`, `to_id`, `properties`, `created_at`, unique per `(project_id, from_id, relationship_type, to_id)`). Holds relationships the extraction engine inferred between facts, grounded to memory ids (or the project hub); PostgreSQL is the source of truth and the projector mirrors each into a Neo4j edge (DEV-22, §6.4/§6.8).
- **Rollback path:** `rollbackMigrations(db, { toVersion })` reverts applied migrations in reverse order using each `down`; `toVersion` stops at (and keeps) that version. The extension installed by 002 is left in place by design (shared database object).
- **Dev reset (pre-release):** `docker exec ppb-postgres psql -U postgres -d codemind_ppb -c "DROP SCHEMA public CASCADE; CREATE SCHEMA public;"` then re-apply — used when a pre-release schema amendment lands.
- **Deviation (recorded):** migrations are TypeScript modules rather than `.sql` files, because the workbench build does not copy loose files into `out/`. The SQL text remains the single source of truth inside the modules.

## 10. Graph repository API (P1-T03 — `node/ppb/graph/graphRepo.ts`)

The only gateway to Neo4j (§6.7). Every method exists because a specification section requires it — deliberately specific, **not a generic ORM**:

| Method | Spec | Purpose |
|---|---|---|
| `createNode` | §6.9 write | strict create; uniqueness enforced by constraint |
| `mergeNode` | §6.9 | idempotent create-or-update for identity nodes re-encountered across segments |
| `ensureProject` | §6.6 | the project's own `Project` node (`id` = `projectId`) |
| `createRelationship` | §6.4/§6.9 | typed relationship; **both endpoints must belong to the same project** |
| `updateNodeStatus` | §6.9/§13 | the only in-place update (versioning transitions) |
| `getNode` / `findNodes` | §6.9/§8.2 | project-scoped read; bounded candidate lookup for dedup/conflict |
| `getRelationships` | §6.9 | directional (`out`/`in`/`both`) and type-filterable |
| `impactAnalysis` | §6.8 | `DEPENDS_ON`/`AFFECTS`/`USES`/`HOSTED_ON`, bounded hops |
| `expandFromSeeds` | §6.8 | retrieval graph expansion (seeds excluded) |
| `history` | §6.8/§13 | `SUPERSEDES` chain (either direction) + `REJECTED` alternatives |
| `retrievePreferences` / `saveGlobalPreference` | §6.6 | the one deliberate exception to per-project scoping |

Rules enforced by construction:

- **Project scoping** — every query carries `projectId`; a missing/empty id throws `PpbGraphError('invalid-project')` *before* any driver call (§6.6/§6.12).
- **No deletes** — there is no delete method; historical information is never silently deleted (§11.5/§13.9).
- **Whitelists** — node and relationship types must come from the ontology (§6.3/§6.4).
- **Error taxonomy** — `invalid-project`, `invalid-node-type`, `invalid-relationship-type`, `invalid-option`, `duplicate-node`, `endpoints-missing`, `driver-failure`.
- **Integer safety** — limits and hop counts are validated and interpolated as integers (Neo4j rejects float parameters).

Verified live against the Route A Neo4j (12 tests) plus 14 unit tests (guards, query shapes, mapping).

## 11. Write path & graph projection (T04/T05/T06/T12, §24)

- **PostgreSQL is the source of truth.** `storage/write.ts#persistFacts` writes `memories` + a `memory_versions` audit row and queues a `neo4j_outbox` row **in one transaction**; a failed statement rolls the whole batch back.
- **The graph is projected asynchronously** by `graph/projector.ts#projectOutbox` — no cross-store transaction; a failed projection stays queued and is retried (idempotent `MERGE`). This is the §24 resolution (2026-09-28).
- **Outbox event kinds:** `memory_upsert`, `decision_upsert`, `event_upsert`, `decision_supersedes`, `decision_rejected`.
- **Category → node type mapping (decision):** `technology_stack→Technology`, `architecture_patterns→Standard`, `business_rules→Constraint`, `engineering_standards→Standard`, `constraints→Constraint`, `developer_preferences→Preference`.
- **Relational read API (IF-11 read half):** `storage/read.ts#findFacts`/`getFact` — always project-scoped.
- **Deduplication (T06):** `extraction/dedup.ts` classifies an incoming fact as `duplicate`/`update`/`contradiction`/`new`; the similarity threshold is a configurable placeholder, and the five §12.3 conflict examples are preserved as fixed cases.

## 12. Embeddings (T07, §9.2/§14)

- **Model:** BGE-M3 (`PPB_EMBED_MODEL`) via an OpenAI-compatible `/embeddings` endpoint (`embeddings/embedder.ts`); every returned vector is validated against the pinned dimension.
- **Dimension:** **configurable** via `PPB_EMBEDDING_DIM` (OD-2 resolved as env-overridable; default 1024), applied consistently to the `vector(N)` column, the embedder's validation and the live-provider check. The deployment in use returns 2048 (DEV-18).
- **Index:** **HNSW** with `vector_cosine_ops` (migration `005_embedding_index`, OD-1 resolved) **when `dim <= 2000`**; a wider model (e.g. 2048) falls back to exact `<=>` cosine search because pgvector cannot index above 2000 dimensions (DEV-18). The vector store queries with `<=>` (cosine distance) to match.
- **Scope:** search joins `memories` so a project never sees another project's vectors.

## 13. Decision & dated-event memory (T12, §10/§11)

- `decisions/decisionMemory.ts`: decisions with `accepted`/`rejected`/`superseded` status (§10.2), rejected alternatives modelled both as an `alternatives` field and as `REJECTED` graph edges to a deterministic Technology node id (§10.3), supersession as a `SUPERSEDES` edge + `superseded_by` link (§10.4), and dated `Event` rows/query (§10.5/§11.3).
