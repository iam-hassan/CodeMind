Overview

What Phase-2 is

Before any prompt reaches the model, CodeMind runs it through a pipeline that gathers and shapes context — so the model answers with the repository, open files, dependencies and intent already in hand.

The engine lives in node/codeMindOrchestrationEngine.ts and node/orchestration/*. It is pure Node (only fs/path/child_process/net/url — no vscode/electron imports), which is exactly why it is testable in isolation. Each user turn passes through seven ordered layers:

The numbers above are a real trace of the turn "Implement a Login Screen using Clerk" — total ≈ 9 ms. That speed is genuine, and the reason is worth stating precisely because it looks suspicious at first glance.

Why 7 layers finish in ~9 ms

Six of the seven layers do pure in-memory string/object work on a ~290-character payload — sub-millisecond each. The one layer that touches disk, toolExecution, is measurably the slowest (6 ms) because it walks the repository for related files. That asymmetry is the fingerprint of real work: if the timings were fake, they would all read 0.

Layer 6 (headroom) did nothing this turn — by design. shouldCompress() returns 'none' below 2000 tokens, and the context here was 61. So compressContext() returns the text unchanged and never loads the compressor. Headroom is a local dynamically-imported module, not a network API, and it never ran.

Layer 7's 0 ms is not the model. It is a hard-coded placeholder that records only the SDK input; the actual model round-trip streams back on a different channel and is never timed by the trace. On this same turn the real round-trip took ≈ 101 s.

Part A
Delivered

The trace moved into its own window

The dev-mode (🐛) trace used to render inside the chat window. It now lives in a dedicated "Orchestration Trace" editor tab, mirroring the existing Multi-Agent Consensus panel — a passive, singleton webview fed by the view pane.

Gotcha — dev mode must be re-synced on reload

The webview restores devModeEnabled from localStorage, but a window reload respawns the worker with the flag false. Without re-posting set_dev_mode, the banner claims "active" while the worker emits zero traces — a silent no-card trap. The restore path now re-posts {type:'set_dev_mode', enabled:true}.

Non-obvious behaviours the suite pins

These are the traps found by writing the tests against the real source — each is now locked so a future edit can't silently regress it:

  • Marker loss on prune. pruneByIntent splits on \n=== , so when the first section is pruned the next survivor keeps its content but loses its leading === marker. Tests assert on the surviving directive text, not the full marker.
  • Cache needs 3 calls to hit. The 30 s result-cache key is sha256(workspace + _lastIntent + openFiles), and _lastIntent updates after the key is computed — so an identical repeat hits on the 3rd call (asserted via phase==='cache_hit', confidence 0.9).
  • Fast path under 20 chars. Short prompts skip the pipeline entirely: prompt unchanged, empty suffix, zero progress events, default metadata.
  • allSettled never rejects. The git adapter on a non-repo still reports status:'success'; the headroom none-path is always headroomAvailable:false.
Part C
Investigated

The "stuck on Thinking…" report

A turn with the Qwen3.8-27B gateway model appeared frozen on "Thinking…". Using the CODEMIND_ENGINE_LOG diagnostic — a redacted JSONL log of every SDK message, enabled only when that env var is set — the real story came out of a 73-line capture.

Verdict: not a hang, not a wrong model, not the layers

The model reached the gateway correctly as Qwen3.8-27B. The turn genuinely ran ≈ 101 s (with a ~22 s mid-stream gateway stall), streamed dozens of deltas, ran TodoWrite successfully — then the model invoked the Task sub-agent tool, which failed, ending the turn with result · subtype: "error_during_execution". The screenshot was taken mid-turn, not after a permanent stall.

Timeline (from the engine log)Event
11:45:10Zstream.start — model Qwen3.8-27B confirmed reaching the gateway
+ deltasdozens of content_block_delta; a ~22 s stall mid-stream
midTodoWrite tool call → tool_result success
lateTask sub-agent tool call → tool_result isError:true
11:46:51Zresult · error_during_execution — turn ends after ≈ 101 s

Why it looked stuck but wasn't: the renderer's queryStream().finally() always posts status:'ready', and the worker's _finalize() resolves on every result subtype — not just success. The UI does recover; the confusion was timing.

Leading hypothesis — unconfirmed

The trigger is the claude_code tool preset, which hands every gateway model Task/TodoWrite/Read/Write. A non-Claude model (Qwen) spawning a nested Task sub-agent is the likely culprit — but the original log recorded only that an errors field existed, not its value. That is exactly what Part D's log enhancement fixes.

Part D
Shipped · compiled clean

Two worker fixes

Both edits are in node/codeMindAgentEngineMain.ts, synced overlay → build tree, and compiled with 0 errors in the 5.7-minute compile-client run.

1 · The trace showed the wrong model (cosmetic)

The trace's layer-7 model field read request.model, fed from this._currentModel — a constructor constant 'claude-opus-5' that setModel() never updated. So the panel always showed claude-opus-5 regardless of the composer selection, even though the real query correctly uses this._settings.model.

// before — a constant setModel() never touched
model: this._currentModel            // always "claude-opus-5"

// after — the single source of truth the SDK query itself uses
model: this._settings.model ?? DEFAULT_MODEL
Verified at runtime

The latest trace paste shows layer 7 as "model":"Qwen3.8-27B" — the composer selection now flows through to the panel. The dead _currentModel field was removed.

2 · The engine log now captures why a tool failed

To answer the open question from Part C, _trace('sdk', …) was extended to record the result's actual error text and any failed tool result — data the old log dropped.

// added to the per-SDK-message trace record
resultInfo:   { subtype, isError, numTurns, text, errors }   // truncated 800
errorToolResult: // content of any tool_result with isError:true
Operations

Build & reproduce

Edits are made in the overlay (vscodium/src/stable/…), then synced to the build tree and compiled. Media (*.js/*.css) copy verbatim; worker .ts changes need a full compile-client.

Reproduce the diagnosis run

# 1 · close every instance (single-instance mutex keeps old code + env)
Get-Process CodeMind -ErrorAction SilentlyContinue | Stop-Process -Force

# 2 · point the engine log at a fresh file
Remove-Item "$env:TEMP\cm_engine.jsonl" -ErrorAction SilentlyContinue
$env:CODEMIND_ENGINE_LOG = "$env:TEMP\cm_engine.jsonl"

# 3 · launch from the same shell — the utility-process worker inherits the env
scripts\run.bat

Then enable 🐛, pick Qwen3.8-27B, send the same turn, and let it run to completion. The refreshed log will hold resultInfo.errors / .text and errorToolResult — the real reason the Task sub-agent died.
